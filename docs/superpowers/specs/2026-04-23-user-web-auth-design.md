# 用户端设计：最小登录闭环与动态菜单

日期：2026-04-23
状态：待审阅
适用仓库：`D:\workspace\projects\aios_practice_platform`

## 1. 背景

当前 `apps/user-web` 已具备阶段 2 的练题、练题记录、错题本、熟题本、疑惑题与班级学习等页面能力，但应用壳层仍直接创建匿名 API client，并使用硬编码按钮切换页面。

在真实后端环境下，用户端页面一加载就会访问受保护接口，因此会统一收到 `401 Unauthorized`。这不是后端认证链路缺失，而是用户端尚未补齐登录、会话恢复、动态菜单与登录失效回退这条最小闭环。

后端与管理端当前已具备以下基础：

1. 后端已实现：
   - `POST /api/v1/auth/login`
   - `POST /api/v1/auth/refresh`
   - `GET /api/v1/auth/me`
   - `POST /api/v1/auth/logout`
   - `GET /api/v1/menus?app_type=user`
2. 管理端 `apps/admin-web` 已实现最小登录页、本地会话存储、菜单拉取与退出登录。
3. 用户端菜单在后端已有正式定义，且会按 access token 中的权限自动过滤。

本次设计的目标，是在不改动后端认证契约、不引入新接口的前提下，为 `user-web` 建立一套最小但正式可用的登录闭环，并将导航入口切换为基于菜单接口的动态渲染。

## 2. 目标

本次改造完成后，应满足：

1. 用户端未登录时，只显示登录页。
2. 登录页显示 `tenant_code / username / password` 三个输入项。
3. 登录成功后，用户端会保存本地会话并拉取 `app_type=user` 的动态菜单。
4. 用户端导航不再写死，而是基于后端返回菜单渲染。
5. 页面刷新后可以恢复本地会话，不要求用户重复登录。
6. 用户主动退出或接口返回 `401` 时，会清理会话并回到登录页。
7. 现有练题、复习、班级学习页面继续复用当前 API SDK，只是改为走带 access token 的 client。
8. SDK 契约不新增认证接口，只复用现有 `login / logout / menus / me`。
9. 前端测试覆盖登录、会话恢复、动态菜单、退出登录和 `401` 回退。

## 3. 范围

### 3.1 包含范围

1. `apps/user-web` 新增最小登录页。
2. `apps/user-web` 新增独立认证状态层，用于管理：
   - 登录结果
   - 本地会话恢复
   - 菜单数据
   - 退出登录
   - 登录失效回退
3. `apps/user-web` 应用壳切换为“未登录显示登录页，已登录显示动态菜单与业务页面”。
4. 用户端导航从硬编码按钮切换为基于 `/menus?app_type=user` 的菜单渲染。
5. 现有业务页面接入带 token 的 API client。
6. 相关前端测试补齐。
7. 设计说明与实现计划文档补齐。

### 3.2 不包含范围

1. 新增后端认证接口。
2. 自动刷新 token。
3. 找回密码、修改密码、首次登录改密。
4. React Router 重构。
5. 多标签页会话同步。
6. 更复杂的用户端布局重构。
7. 将管理端和用户端认证层立即抽成共享包。

这些能力可以在后续“认证增强”或“前端壳层治理”阶段再单独设计。

## 4. 可选方案与结论

### 4.1 方案一：直接复用管理端的最小模式

做法：

1. 在 `user-web` 中复制管理端的登录表单与本地存储模式。
2. 保留当前组件内状态管理。
3. 只补登录、登出和菜单拉取。

优点：

1. 实现最快。
2. 改动最小。
3. 与现有管理端风格一致。

缺点：

1. 用户端认证相关状态仍散落在 `app.tsx` 内。
2. 后续老师端、学生端共存时，状态扩展会再次拆分。

### 4.2 方案二：在用户端新增独立 auth store

做法：

1. 在 `user-web` 内建立轻量认证状态层。
2. 将登录、会话恢复、菜单保存、登出、登录失效回退集中管理。
3. `app.tsx` 只消费认证状态和当前 client。

优点：

1. 结构更清晰。
2. 更适合后续继续扩展用户端页面与角色差异。
3. 能避免 `app.tsx` 持续膨胀。

缺点：

1. 比方案一多出一层抽象。
2. 本次改动面略大于最小复制方案。

### 4.3 方案三：立即抽共享认证壳到公共包

做法：

1. 将管理端和用户端的登录、会话、菜单逻辑统一抽入共享包。
2. 两端共用同一套认证容器。

优点：

1. 长期最统一。
2. 复用价值最高。

缺点：

1. 当前范围过大。
2. 会把用户端登录阻塞问题扩大成跨应用重构。

### 4.4 结论

本次采用方案二：

1. 在 `user-web` 内新增独立 `auth store`。
2. 复用管理端已经验证过的最小登录闭环模式。
3. 不在本次把管理端和用户端认证层强行合并。

这样既能解决当前 `401` 阻塞，又能为后续用户端继续增长时保留清晰边界。

## 5. 核心设计

### 5.1 页面形态

用户端应用分为两种状态：

1. 未登录态：
   - 展示登录页；
   - 不渲染业务菜单；
   - 不创建匿名业务 client；
   - 不主动请求练题、分析等受保护接口。
2. 已登录态：
   - 展示当前登录用户信息；
   - 展示动态菜单；
   - 展示当前业务页面；
   - 提供退出登录入口。

登录页字段固定为：

1. `tenant_code`
2. `username`
3. `password`

不额外做租户自动推断，也不隐藏租户编码输入项。

### 5.2 前端结构建议

建议在 `apps/user-web/src` 内新增以下文件：

```text
auth-types.ts
auth-store.ts
login-page.tsx
menu-nav.tsx
```

职责划分：

1. `auth-types.ts`
   - 存放用户端会话类型；
   - 例如 `UserSessionState`、登录动作结果等。
2. `auth-store.ts`
   - 负责 `load / save / clear`；
   - 管理当前 session、错误信息、是否已初始化；
   - 对外提供登录、登出、恢复会话、失效回退等动作。
3. `login-page.tsx`
   - 只负责渲染登录表单与提交反馈；
   - 不直接操作业务页面。
4. `menu-nav.tsx`
   - 根据菜单树渲染用户端导航；
   - 将点击结果回传给应用壳。
5. `app.tsx`
   - 只负责应用状态切换；
   - 根据 session 创建带 token 的 API client；
   - 根据当前路径装配现有页面。

本次不强制引入 Zustand。若当前实现使用 React `useState + useMemo + localStorage` 即可满足需求，则优先保持依赖简单；“auth store”在这里指职责明确的认证状态层，而不是必须引入新的状态库。

### 5.3 会话模型

用户端本地会话建议包含：

```ts
interface UserSessionState {
  accessToken: string;
  refreshToken: string;
  expiresIn: number;
  menus: MenuItem[];
  user: CurrentUser;
}
```

存储规则：

1. 使用浏览器 `localStorage`。
2. 独立 key 使用：
   - `aios.user.session`
3. 存储值为 JSON 字符串。
4. 解析失败时视为无效会话并清除。

### 5.4 登录链路

登录流程如下：

1. 用户提交 `tenant_code / username / password`。
2. 前端调用 `POST /api/v1/auth/login`。
3. 登录成功后，使用返回的 `access_token` 调用：
   - `GET /api/v1/menus?app_type=user`
4. 将以下数据一次性写入本地会话：
   - `access_token`
   - `refresh_token`
   - `expires_in`
   - `user`
   - `menus`
5. 进入已登录态。
6. 如果当前没有选中路径，则默认选中第一个可用菜单路径。

如果登录成功但菜单拉取失败，则本次登录流程整体视为失败，不保留半登录状态。

### 5.5 启动恢复链路

应用启动时：

1. 先从 `localStorage` 读取 `aios.user.session`。
2. 若无会话，直接进入登录页。
3. 若会话反序列化失败，清理存储并进入登录页。
4. 若会话恢复成功，则进入已登录态。
5. 已登录态下再基于 `accessToken` 创建 API client。

本次启动恢复不强制额外调用 `GET /auth/me` 做二次校验，原因如下：

1. 当前目标是先补齐最小闭环，减少首次范围。
2. 后续业务接口若返回 `401`，仍会统一触发失效回退。
3. 是否在启动阶段主动校验 token，可在后续认证增强阶段再评估。

### 5.6 动态菜单

用户端菜单统一来源于：

```text
GET /api/v1/menus?app_type=user
```

前端不再硬编码固定按钮列表。

渲染规则：

1. 一级菜单和子菜单均按后端返回顺序展示。
2. 用户最终点击的是具体功能路径。
3. 若菜单树为空，显示：
   - “当前账号暂无可用功能”
4. 若当前选中路径不在本次菜单中，则回退到第一个可用路径。

这样可确保：

1. 没有 `analytics:view` 的账号不会看到“班级学习”；
2. 只有 `practice:use` 的账号只看到练题相关入口；
3. 老师与学生若权限不同，可在不改前端写死逻辑的情况下得到不同入口。

### 5.7 页面映射

当前页面映射保持现有最小壳层方式，不引入 React Router。

建议路径映射如下：

1. `/app/courses`
   - 继续显示当前“我的课程”页面内容。
2. `/app/practice`
   - `PracticePanel`
3. `/app/practice/results/:id`
   - `PracticeResultPage`
4. `/app/practice/history`
   - `PracticeHistoryPage`
5. `/app/practice/history/:id`
   - `PracticeSessionDetailPage`
6. `/app/practice/wrong`
   - `PracticeStateListPage(stateType="wrong")`
7. `/app/practice/mastered`
   - `PracticeStateListPage(stateType="mastered")`
8. `/app/practice/confused`
   - `PracticeStateListPage(stateType="confused")`
9. `/app/class-learning`
   - `ClassLearningPage`

路径字符串仍由应用壳维护，避免本次把认证改造扩展成整套路由治理。

### 5.8 401 回退机制

当已登录态下任一受保护接口返回 `401` 时，前端应执行统一动作：

1. 清空本地会话；
2. 清空当前选中路径与临时业务状态；
3. 返回登录页；
4. 展示提示：
   - “登录已失效，请重新登录”

本次不做自动 refresh token 重试，原因如下：

1. 当前问题是完全缺失登录闭环，不是 token 刷新失败。
2. 自动刷新会引入更多竞态和错误分支。
3. 先保证“失败后明确回登录页”比“隐式补救”更可控。

### 5.9 退出登录

退出登录流程：

1. 调用 `POST /api/v1/auth/logout`。
2. 无论接口成功或失败，都清理本地会话。
3. 返回登录页。
4. 清空密码输入框。

这样可以避免后端偶发异常时，前端仍被卡在伪登录状态。

## 6. 错误与状态

### 6.1 登录页状态

1. 提交中：
   - 登录按钮禁用；
   - 页面显示“登录中...”或等效提交反馈。
2. 登录失败：
   - 展示后端返回错误消息；
   - 保留 `tenant_code` 与 `username`；
   - 清空或允许重新编辑 `password`。

### 6.2 应用页状态

1. 会话恢复中：
   - 可显示轻量“正在恢复登录状态...”。
2. 菜单为空：
   - 显示“当前账号暂无可用功能”。
3. 业务 API 失败且非 `401`：
   - 保留当前登录态；
   - 由各业务页面继续使用现有错误提示逻辑。
4. 业务 API 返回 `401`：
   - 统一回登录页。

## 7. 对现有实现的影响

### 7.1 `apps/user-web`

需要调整：

1. `app.tsx`
   - 从匿名 client 入口改为认证驱动入口。
2. 现有硬编码导航
   - 改为菜单驱动渲染。
3. API client 创建时机
   - 改为依赖 `session.accessToken`。

### 7.2 `packages/api-sdk`

本次不要求新增认证接口，只复用已有：

1. `login`
2. `logout`
3. `menus`
4. `me`

如果为统一 `401` 处理需要在 client 选项层增加错误钩子，应保持为向后兼容的可选能力，不能破坏现有管理端与测试代码。

### 7.3 管理端

本次不修改 `apps/admin-web` 行为。

若后续证明用户端 `auth store` 设计稳定，可再评估是否抽取公共认证层。

## 9. 验收标准

满足以下条件即可视为本次完成：

1. 打开 `user-web` 时，未登录不会再主动触发一串 `401` 业务请求。
2. 用户可以通过 `tenant_code / username / password` 成功登录。
3. 登录后菜单来自 `/menus?app_type=user`，而不是前端写死。
4. 页面刷新后仍保持登录态。
5. 退出登录后回到登录页。
6. token 失效或接口返回 `401` 后，前端能自动清理会话并要求重新登录。
7. 前端测试、类型检查、构建通过。

## 10. 风险与后续

当前设计的主要限制：

1. 不做自动 refresh token，因此 token 过期后会直接回登录页。
2. 不做多标签页同步，不保证多个标签页的会话变更即时一致。
3. 当前仍是路径字符串驱动页面切换，不是完整路由体系。

后续可以拆分的新阶段包括：

1. 用户端 token 自动刷新。
2. 用户端与管理端共享认证壳。
3. React Router 正式接入。
4. 更完整的首页、课程页与角色化入口布局。
