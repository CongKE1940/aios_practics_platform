# 阶段 3A 设计：考试主链路最小闭环

日期：2026-04-23
状态：已确认设计，待用户审阅

## 1. 背景

当前项目已完成：

1. 阶段 1 基础平台能力：认证、多租户、组织课程、RBAC、公告通知、文件资产占位接口。
2. 阶段 2A 题库与题目管理：题库下发、题目版本化、管理端题源闭环。
3. 阶段 2B 模板下载与导入：题目、题库、考试模板下载，题目与题库同步导入。
4. 阶段 2C 到 2F：学生练题闭环、课程来源练题、老师侧班级学习分析、单题详情与基础老师讲评。

现阶段最明显的主链路缺口，是 PRD 中明确要求的考试能力仍停留在 DDL 与 OpenAPI 设计层，尚未形成正式实现。仓库内已有：

- `010_exams.sql` 中的考试域表结构；
- `docs/docs/openapi_design_v1.md` 中的考试接口草案；
- 前端页面规划中的考试列表、考试详情、考试作答、考试结果、老师考试发布页；
- 测试与验收文档中的考试验收要求。

因此，下一步需要把考试相关设计真正落成一个可运行、可联调、可验收的最小闭环。

## 2. 目标

本次设计的目标，是定义“考试主链路最小闭环”的正式实现边界，使项目在不引入监考、防作弊、主观题阅卷等复杂能力的前提下，先完整打通：

1. 老师在用户端创建考试、编辑考试、配置发布对象、配置固定试卷或随机组卷规则。
2. 老师发布考试，系统在发布时固化试卷内容与题目版本快照。
3. 学生查看自己的考试列表，进入考试详情，开始考试，自动保存答案，手动交卷或超时自动交卷。
4. 系统对客观题自动判分，返回考试结果，并将考试错题沉淀到用户题目状态。
5. 全过程遵循现有多租户、RBAC、教师任课范围、题目版本快照与练题/考试严格分离规则。

## 3. 非目标

本次设计明确不包含以下能力：

1. 防作弊：切屏检测、设备绑定、IP 限制、摄像头监考。
2. 主观题、人工阅卷、阅卷流程、批注与考试讲评。
3. 多次作答、补考、重考、重置考试次数。
4. 考试导入落库；考试模板继续仅支持下载。
5. 复杂考试统计大屏、管理端全局考试看板。
6. 成绩申诉、考试复核、人工改分。
7. Redis 倒计时同步、分布式锁基础设施的完整生产级建设；本轮只保留接口与实现约束。

4. 选择发布对象：

5. 保存草稿。
6. 发布考试。

### 4.2 用户端学生侧

本轮新增学生考试最小入口：

1. 我的考试列表。
2. 考试详情页。
3. 考试作答页。
4. 考试结果页。

学生可完成：

1. 查看自己被命中的考试。
2. 在时间合法范围内开始考试。
3. 在作答过程中自动保存答案。
4. 手动交卷。
5. 超时后自动交卷。
6. 查看考试结果。

### 4.3 后端考试模块

本轮新增正式模块：

- `internal/modules/exam`

该模块负责：

1. 考试定义管理。
2. 组卷与发布。
3. 学生作答。
4. 自动判分与结果查询。
5. 考试错题沉淀。

## 5. 核心业务规则

### 5.1 作答次数

同一学生对同一考试，第一版只允许一次正式作答。

具体规则：

1. 首次开始考试时创建唯一 `exam_attempt`。
2. 再次开始同一考试时：
   - 若已有 `in_progress` attempt，则返回该 attempt；
   - 若已有 `submitted` 或 `timeout_submitted` attempt，则拒绝重新开始。

### 5.2 自动保存与超时交卷

第一版必须支持：

1. 自动保存答案；
2. 超时自动交卷。

自动保存要求：

1. 每次保存按 `attempt_id + display_order` 精确定位。
2. 同一题重复保存执行覆盖更新。
3. 自动保存接口必须幂等。

超时自动交卷要求：

1. 若学生在截止时间或时长耗尽前未手动交卷，服务端在提交接口与结果查询口径中都必须识别超时；
2. 首个命中超时条件的写操作负责完成自动交卷；
3. 超时交卷后的状态标记为 `timeout_submitted`。

### 5.3 练题与考试严格分离

考试能力必须继续遵守已有设计原则：

1. 练题会话与考试作答严格分表。
2. 熟题过滤绝不能影响考试题目。
3. 考试错题会沉淀到 `exam_wrong_count`。
4. 考试不得生成熟题标记。
5. 疑惑题也不在本轮考试作答页暴露。

### 5.4 快照与可回放

考试发布后必须固定题目内容口径：

1. 试卷题目保存 `question_id + question_version_id`。
2. 试卷题目保存 `snapshot_content_json`。
3. 若考试时随机展示选项顺序，必须保存 `presented_options_json`。
4. 学生结果页优先读取考试快照，不回读当前最新题目版本。

## 6. 数据模型使用方式

本轮直接使用现有 DDL 中已定义的考试域表：

1. `exams`
2. `exam_targets`
3. `exam_papers`
4. `exam_paper_question_rules`
5. `exam_paper_questions`
6. `exam_attempts`
7. `exam_attempt_answers`

### 6.1 exams

考试主体，存放：

1. 基础信息：名称、说明、开始结束时间、时长。
2. 模式：`fixed` / `random_assembly`。
3. 状态：草稿、已发布、已关闭、已取消。
4. 创建人、所属租户。

### 6.2 exam_targets

考试发布对象表，保存：

1. `class`
2. `course`
3. `user`

每条记录只表达一个命中对象，避免在 `exams` 主表中堆 JSON 目标结构。

### 6.3 exam_papers / exam_paper_question_rules / exam_paper_questions

设计原则：

1. 老师无论选择固定试卷还是随机组卷，发布后都统一生成一份固定试卷。
2. 学生作答永远只面向已生成的固定试卷。
3. 两种模式的差异只发生在发布前。

具体口径：

1. `fixed` 模式：
   - 老师直接提交题目列表；
   - 发布时写入 `exam_paper_questions`。
2. `random_assembly` 模式：
   - 老师提交组卷规则；
   - 草稿阶段写入 `exam_paper_question_rules`；
   - 发布时执行候选题统计、抽题、缺口校验；
   - 成功后写入 `exam_paper_questions`。

### 6.4 exam_attempts / exam_attempt_answers

1. `exam_attempts` 表示某个学生对某场考试的一次正式作答。
2. `exam_attempt_answers` 按题逐条保存学生提交的答案和判题结果。
3. 第一版 `exam_attempts` 保持一个学生一场考试唯一记录。

## 7. 考试模式设计

### 7.1 固定试卷模式

老师在草稿中直接提交题目列表：

1. 指定题目 ID。
2. 指定题目版本 ID。
3. 指定展示顺序。
4. 指定分值。

保存草稿时不立即生成最终纸面快照；发布时统一固化到 `exam_papers` 与 `exam_paper_questions`。

这样可以保持：

1. 草稿阶段仍可编辑；
2. 发布后题目内容固定；
3. 与随机组卷共用后续学生作答链路。

### 7.2 随机组卷模式

老师在草稿中提交规则列表，规则维度收敛为：

1. `question_type`
2. `question_count`
3. `score_per_question`
4. `bank_ids`
5. `course_id`
6. `knowledge_tag_ids`
7. `per_knowledge_count`

发布时服务端执行：

1. 校验发布人权限；
2. 校验目标可见题库范围；
3. 统计候选题池；
4. 按题型与知识点规则抽题；
5. 若不足，返回详细缺口；
6. 成功后固化为正式试卷题目。

## 8. 状态机设计

### 8.1 考试状态

第一版 `exams.status` 收敛为：

1. `draft`
2. `published`
3. `closed`
4. `cancelled`

状态规则：

1. `draft`：
   - 允许编辑基础信息、目标、题目或组卷规则；
   - 允许发布。
2. `published`：
   - 不允许再修改题目和规则；
   - 允许查看、作答、结果统计；
   - 超过结束时间后可视为结束态，但仍保留 `published` 数据意义；
   - 管理动作上可显式关闭。
3. `closed`：
   - 不再允许开始考试；
   - 保留结果查看。
4. `cancelled`：
   - 考试取消；
   - 不允许参加。

### 8.2 作答状态

第一版 `exam_attempts.status` 收敛为：

1. `in_progress`
2. `submitted`
3. `timeout_submitted`

状态规则：

1. 开始考试创建 `in_progress`。
2. 学生主动交卷变更为 `submitted`。
3. 因超时完成交卷变更为 `timeout_submitted`。

## 9. API 设计收口

本轮正式实现以下接口：

### 9.1 老师侧考试定义与发布

1. `GET /api/v1/exams`
2. `POST /api/v1/exams`
3. `GET /api/v1/exams/{id}`
4. `PUT /api/v1/exams/{id}`
5. `POST /api/v1/exams/{id}/publish`

### 9.2 学生作答与结果

1. `POST /api/v1/exams/{id}/attempts`
2. `GET /api/v1/exam-attempts/{id}`
3. `POST /api/v1/exam-attempts/{id}/answers`
4. `POST /api/v1/exam-attempts/{id}/submit`
5. `GET /api/v1/exam-attempts/{id}/result`

### 9.3 关于 `generate-paper`

`POST /api/v1/exams/{id}/generate-paper` 本轮不作为前端直调正式能力开放。

原因：

1. 对固定试卷与随机组卷来说，发布后最终都只需要一份正式试卷；
2. 若前端先生成试卷、再改草稿、再发布，会引入中间态不一致；
3. 当前最小闭环更适合把“预检查 + 生成试卷 + 发布通知”收口到一个发布动作里。

因此本轮策略是：

1. 固定试卷：发布时固化题目。
2. 随机组卷：发布时做缺口校验并生成试卷。

后续若需要“先预览组卷结果再发布”，再单独扩展预检查或试卷预览接口。

## 11. 权限与可见范围

### 11.1 创建与发布权限

第一版沿用既有 RBAC 风格，要求：

1. 老师创建、编辑、发布考试需要 `exam:publish` 权限。
2. 学校管理员、系统管理员可按当前租户范围管理考试。

### 11.2 发布对象范围校验

当创建人是老师时：

1. 发布到 `class`：必须是当前任课班级。
2. 发布到 `course`：必须是当前任课课程。
3. 发布到 `user`：目标学生必须落在老师当前可见的班级课程范围内。

当创建人是学校管理员或系统管理员时：

1. 按当前 token 的租户范围校验；
2. 不允许跨租户发布。

### 11.3 学生可见范围

学生只能看见命中自己的考试：

1. 通过班级命中；
2. 通过课程命中；
3. 通过指定学生命中。

若考试通过多种方式同时命中，前端仍只显示一条考试记录。

## 12. 结果沉淀规则

### 12.1 自动判分

本轮只处理客观题：

1. 单选；
2. 多选；
3. 判断。

判分口径：

1. 保存答案时不立即返回最终总分；
2. 交卷时统一计算客观题得分；
3. 结果页展示：
   - `final_score`
   - `objective_score`
   - `subjective_score=0`

### 12.2 错题沉淀

交卷后：

1. 错题写入 `user_question_states.exam_wrong_count`；
2. 不更新 `practice_correct_count`；
3. 不更新 `practice_wrong_count`；
4. 不写入 `is_mastered`；
5. 不因为考试结果改变熟题状态。

## 13. 错误处理

第一版必须显式处理以下错误：

1. 缺少 `exam:publish` 权限：403。
2. 发布对象越权：403。
3. 组卷题量不足：400，返回缺口详情。
4. 考试未发布或已取消：不可开始。
5. 考试未到开始时间或已超过结束时间：不可开始。
6. 同一学生重复开始已提交考试：409 或明确业务错误。
7. 非本人 attempt 查询或提交：404 或 403，保持租户与用户隔离。
8. 交卷后再次保存答案：拒绝修改。
9. 超时后再次交卷：返回已提交结果，不重复判分。

## 14. 第一轮测试与验收点

本轮验收聚焦以下能力：

1. 仅老师及以上角色可创建考试。
2. 固定试卷考试可成功创建、编辑、发布。
3. 随机组卷考试可成功创建、发布。
4. 随机组卷题量不足时发布被阻止，并返回缺口说明。
5. 发布对象支持班级、课程、指定学生。
6. 学生只能看到命中自己的考试。
7. 学生开始考试后只生成一条正式 attempt。
8. 自动保存重复调用保持幂等。
9. 手动交卷可成功判分。
10. 超时交卷有效。
11. 考试结果优先使用快照数据回放。
12. 考试错题沉淀有效，但不生成熟题标记。

## 15. 实现顺序建议

这份设计对应的实现顺序建议为：

1. 后端 exam 模块骨架与红测。
2. 老师侧考试定义与发布接口。
3. 学生侧开始考试、保存答案、交卷、结果接口。
4. SDK 契约补齐。
5. 用户端老师考试页。
6. 用户端学生考试列表、详情、作答、结果页。
7. OpenAPI、阶段状态文档与测试收口。

## 16. 设计结论

本次考试主链路最小闭环采用以下核心策略：

1. 老师在用户端创建并发布考试。
2. 发布对象第一版即支持班级、课程、指定学生。
3. 考试模式第一版即支持固定试卷与随机组卷。
4. 学生对同一考试只允许一次正式作答。
5. 自动保存与超时自动交卷都进入第一版。
6. 发布后统一生成固定试卷，学生永远只面对固化后的试卷。
7. `generate-paper` 本轮不作为前端直调正式接口，而是收口到发布流程内部。

这样可以在当前项目基础上，以最小但完整的方式打通“老师能发、学生能考、系统能判、结果能看”的正式考试主路径。
